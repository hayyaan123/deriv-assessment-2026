# Grounded Q&A Assistant (RAG)

A small assistant that answers questions from a local knowledge base (`docs/`) and returns
grounded answers with chunk-level citations. Questions the documents don't cover are answered with
"The knowledge base does not provide enough information to answer this."

Every pipeline stage writes its output to `artifacts/`, so each step can be inspected on its own.

## Setup

Requires Python 3.10+.

```bash
git clone https://github.com/hayyaan123/deriv-assessment-2026.git
cd deriv-assessment-2026
python3 -m pip install -r requirements.txt
```

Optional: to generate answers with Gemini, create a `.env` file in the project root:

```
GEMINI_API_KEY=your_key_here
# optional, defaults to gemini-3.8-flash
GEMINI_MODEL=gemini-3.5-flash-lite
```

Get a free key at https://aistudio.google.com. `.env` is gitignored. **Without a key the project
still runs** (see [Offline fallback](#offline-fallback)).

## Run

```bash
python3 run.py        # runs the full pipeline and regenerates every artifact
python3 validate.py   # checks the artifacts; exits 1 if any check fails
```

Example output:

```

To use a different knowledge base, replace the files in `docs/` (any `.md` or `.txt`) and
`questions.json` (same schema: `[{"id": ..., "question": "..."}]`), then run `python3 run.py` again.
No filenames, question order or answers are hardcoded.

## Pipeline

| Stage | What happens | Artifact |
|---|---|---|
| `DOCUMENTS_LOADED` | Every `.md`/`.txt` file in `docs/` is read | `documents.json` |
| `CHUNKS_CREATED` | Documents are split into overlapping chunks | `chunks.json` |
| `INDEX_BUILT` | A TF-IDF index is built from the chunks at runtime | (in memory) |
| `QUESTIONS_LOADED` | `questions.json` is read and checked | — |
| `RETRIEVAL_COMPLETE` | Top 3 chunks per question by cosine similarity | `retrieval_results.json` |
| `ANSWERS_GENERATED` | The LLM answers from the retrieved chunks only | `answers.json`, `llm_calls.jsonl` |
| `CITATIONS_VALIDATED` | Deterministic citation and grounding checks | `citation_validation.json` |
| `RESULTS_EXPORTED` | Everything is combined per question | `final_answers.json` |
| `VALIDATION_COMPLETE` | `validate.py` checks are run on the files written | — |

## Design choices

- **Chunking:** 500-character windows with 100 characters of overlap (`CHUNK_SIZE`, `CHUNK_OVERLAP`
  in `run.py`). Chunk ends snap back to a paragraph, sentence or word break and starts snap
  forward to a word break, so chunks don't cut words in half. IDs are stable and readable:
  `<doc_id>::chunk_<n>` (e.g. `webhooks::chunk_1`).
- **Retrieval:** TF-IDF (unigrams + bigrams, English stop words removed) with cosine similarity,
  via scikit-learn. It is local, deterministic and needs no API call. For a knowledge base this
  small it is accurate enough; embeddings would be the next step for larger or more varied docs.
- **Answer generation:** the prompt contains only the 3 retrieved chunks, each labelled with its
  `chunk_id`. It tells the model to answer only from that context, not to invent features or
  policies, to cite the chunk IDs it used, and to return the exact "not enough information"
  sentence with empty citations when the context doesn't cover the question. The model returns
  JSON, which is parsed (tolerating markdown code fences) and type-checked.
- **Citation validation** is plain code, not another LLM call. For each answer it checks that:
  1. every cited chunk ID was actually retrieved for that question,
  2. a supported answer has at least one citation,
  3. an unsupported answer has no citations,
  4. **grounding check:** every number in a supported answer appears in the cited chunks
     (`1,000` and `1000` count as equal). Wrong limits, prices and durations are the most
     damaging hallucinations for this kind of knowledge base.

  Failed answers are reported, not silently rewritten, so model errors stay visible.
- **Failure handling:** rate-limit (429) errors are retried twice with a backoff (5s, 10s). If the
  LLM call still fails or returns unparseable output, that question falls back to the offline
  extractive answer below, and the reason is recorded in `llm_calls.jsonl`. The pipeline never
  crashes on a single bad call.

## Offline fallback

When no `GEMINI_API_KEY` is set, answers are generated by a simple rule-based method:

- If the top retrieved chunk scores below `FALLBACK_MIN_SCORE` (0.15), the question is answered as
  unsupported.
- Otherwise, the answer is the sentence from the top chunk that shares the most terms with the
  question, citing that chunk.

These answers are less fluent than the LLM's, but they are always taken verbatim from the
documents and go through the same validation.

## `validate.py`

Standalone and standard-library only. It checks that:

- all required artifact files exist
- all JSON (and each `llm_calls.jsonl` line) is valid
- every question has exactly one answer
- each question has at most 3 retrieved chunks
- every cited chunk ID exists and was retrieved for that question
- unsupported answers have no citations
- supported answers have citations

## LLM call log

Each Gemini call appends one line to `artifacts/llm_calls.jsonl` with the stage, timestamp,
provider, model, question ID, a SHA-256 hash of the prompt, the input and output artifacts, and a
status (`ok`, or the error and fallback used).

The committed artifacts were generated with `gemini-3.5-flash-lite`.

## Limitations

- Citations are per answer, not per sentence: an answer citing two chunks doesn't say which
  sentence came from which.
- The grounding check only verifies numbers. A wrong non-numeric claim with a valid citation would
  pass; checking key answer terms against the cited text would be the next step.
- The fallback threshold (0.15) is a heuristic tuned on the sample documents.

## Project structure

```
